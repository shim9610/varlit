# 다종 블록 append·동시 조회 비교 설계

상태: **설계이며, 아래 주 시험의 외부 엔진 비교는 아직 실행하지 않았다.** 기존 단일 payload·수치 배열 측정을 이 설계의 결과로 대신하지 않는다. 현재 PR 런타임 및 안전성 검증과도 별도다.

## 성능 기준과 논리 모델

SQLite 대비 같은 성공 작업에서 최소 2배의 처리량, 즉 소요 시간은 절반 이하가 목표다. 쓰기·새 데이터 따라 읽기·키 조회는 각각 판정한다. 한 항목의 개선으로 다른 항목을 상쇄하지 않는다. HDF5도 같은 데이터와 지원하는 조회 의미에서 함께 비교한다. 두 배 달성이나 달성 가능성은 측정 전에 보장하지 않는다.

대표 모델은 [고카디널리티 시험의 CardinalityFormat](../../crates/varlit/tests/high_cardinality.rs)에 근거한다. 이 포맷은 고정 Metadata(run)와 가변 Frame(scan, frame, payload)를 함께 선언하고, Frame의 복합 키를 디스크 색인에 둔다. [선언형 키 시험](../../crates/varlit/tests/schema_key_kinds.rs)은 유한 키와 일반 키의 구분도 제공한다. `high-cardinality-dev`는 0.10.0에서 제거됐으며 고카디널리티 경로는 `key_index = disk`를 선언한 indexed API에서 제공된다.

- 논리 Frame 하나는 애플리케이션이 정의한 데이터 블록이다. 블록 안의 개별 수치 샘플을 별도 프레임으로 쪼개지 않는다.
- 고정 메타데이터와 가변 데이터 블록을 같은 파일에 섞어 추가한다. 버전이 있는 메타데이터, 작은 독립 객체와 큰 샘플 청크의 역할을 구분한다.
- 블록 수, 블록별 payload 크기, payload 안의 샘플 수, 키 개수, 커밋 수를 별도로 기록한다.
- 고카디널리티 시험의 독립 객체 수와 샘플 배열의 원소 수를 혼동하지 않는다.

## 주 시험

| 작업 | 데이터 및 상태 | 조회와 비교 결과 |
|---|---|---|
| 혼합 순차 로깅 | 고정 Metadata와 64 KiB·1 MiB 가변 Frame을 혼합 append | 타입별 값과 순서, 전체 payload를 검증 |
| 복합 크기·타입 | 작은 독립 메타데이터와 크기가 다른 Frame을 섞음 | 타입 필터, 지정 구간, 새로 커밋된 접미부 |
| 동시 공유 | writer 1개, reader 1개·8개, 유지한 이전 스냅샷 | 새 데이터 follow, 키 조회, 이전 스냅샷 불변성 |
| 고카디널리티 | 일반 복합 키 10만·100만 개와 고정 캐시 | 키별 조회, append/follow 비용, RAM·색인·임시 공간 증가 |
| 갱신 이력 | 같은 키의 새 버전을 append하는 별도 조건 | 게시 시점의 최신 값, 이전 스냅샷 값; 순수 추가와 별도 판정 |
| 긴 실행·빈 폴링 | 충분히 긴 기존 접두부 뒤에 작게 추가하거나 추가 없음 | 빈 follow의 반복 비용과 새 데이터 양에 따른 비용 |

일반 로그에서 `push_iter`·배치 API를 사용한다. scalar push가 실제 필요한 조건도 별도 표시한다. 한 번의 open·bootstrap·색인 구성 비용은 반복 조회와 분리한다. reader는 핸들과 커서를 유지하며 매번 open하거나 전체 파일을 스캔하지 않는다.

writer는 reader의 처리 완료를 기다려 강제로 느린 속도에 맞추지 않는다. 각 reader가 같은 개수·바이트를 실제로 소비하게 하고, writer 완료와 전체 소비 완료를 따로 기록한다. 미커밋 데이터는 조회 결과로 인정하지 않으며 공통된 게시 경계를 사용한다. 엔진마다 다른 장애 복구·내구성 의미를 같은 보장으로 단정하지 않는다.

## 엔진별 정상 저장 방식

### Varlit

선언된 fixed/variable 블록, 생성된 stream/indexed handle, 배치 append, 유지한 typed cursor와 명시적 follow를 사용한다. `key_index = disk`, 유한 키, 일반 고카디널리티 키, resident/nonresident 정책은 해당 작업에서 구분한다. 일반 키 개수가 Varlit HashMap의 크기로 증가하지 않는다는 기존 계약을 실제 메모리와 함께 확인한다.

matrix/수치 배열은 그 자료형에 적합한 보조 시험이다. 이것으로 혼합 블록 append의 성능을 대체하지 않는다. mmap의 불변성 조건과 CRC 검증을 유지하며, 필요한 compaction·초기화 비용을 숨기지 않는다.

### SQLite

논리 블록 종류와 필드에 맞춘 테이블·타입을 선언한다. 샘플 배열을 담은 Frame은 적절한 BLOB 배치를 허용하고, 메타데이터 필드는 실제 조회에 맞는 컬럼으로 둔다. 큰 배열의 각 샘플을 억지로 한 행으로 저장하지 않는다.

순차 로그의 sequence 기본키와 필요한 복합 키 색인을 제공한다. 예를 들어 Frame의 최신 버전 조회에는 `(scan, frame, sequence DESC)` 색인, follow에는 sequence 범위를 사용한다. 타입별 테이블과 전역 로그 테이블 중 요구한 순서·조회 결과를 충족하는 설정을 비교한다. 필요 없는 색인을 추가해 쓰기를 느리게 만들지 않는다.

prepared statement, 같은 게시 단위의 transaction, WAL 및 FULL 동기화, 실제 페이지 크기·캐시·mmap 설정을 기록한다. 부분 BLOB 조회에는 부분 읽기 API를 허용한다. 모든 요구 조회를 지원하는 **완결된 스키마와 설정**을 고정한 뒤 쓰기·조회·공간을 함께 측정한다. 색인 없는 쓰기 결과와 색인 있는 조회 결과를 비용 없이 합쳐 가상의 성능으로 제시하지 않는다.

### HDF5

블록 종류별 적합한 compound/배열 dataset을 둔다. 고정 payload는 청크 배열, 가변 payload는 자료형에 맞는 payload 영역과 offset/length 정보를 사용한다. 논리 항목마다 dataset이나 attribute를 생성하는 병적인 배치는 피한다. 청크 크기, chunk cache, 일괄·부분 hyperslab I/O를 실제 데이터에 맞게 선택한다.

동시 append/read는 SWMR을 사용하고, 여러 dataset의 공개된 논리 접두부를 식별하는 commit 정보와 flush/refresh 순서를 명시한다. 전체 데이터와 메타데이터가 같은 게시 경계에서 검증되는지 확인한다. 단순히 파일이 길어졌다는 이유로 미완성 블록을 읽지 않는다.

HDF5 자체에는 SQLite와 같은 범용 복합 키 SQL 색인이 없다. 데이터의 축으로 직접 표현할 수 있는 키는 해당 축을 이용한다. 임의 키 조회에 별도 색인이 필요하면 그 구현과 생성·갱신·open·캐시·저장 비용을 함께 명시해야 한다. 이를 마련하지 않은 상태에서 전체 스캔을 키 조회의 유일한 HDF5 구현으로 삼거나, 같은 기능을 비교했다고 주장하지 않는다. 공통 기능의 append/follow 비교와 범용 키 조회 비교의 범위를 구분한다.

## 측정과 보존

- 기존 4 CPU / 16 GiB / 32 GiB 예산을 유지한다. 제한이나 검증을 제거해 속도를 통과시키지 않는다.
- 같은 논리 데이터·순서·조회·공개 경계·최종 결과를 검증한다. datatype과 물리 배치가 다르다는 이유로 작업량을 줄이지 않는다.
- 초기 스키마 튜닝은 본 측정과 분리하고, 본 측정 전에 완결된 비교 설정을 고정한다.
- writer 시간·CPU, reader 시간·CPU, 전체 완료, 지연 누적, 실제 처리 바이트, RSS/PSS, 저장 공간·WAL·삭제된 열린 파일을 기록한다. mmap의 중복 RSS 계수와 실제 물리 메모리를 구분한다.
- 초기화·검증 oracle·자료 생성·checkpoint/compaction의 포함 범위를 지표별로 명시한다. 애플리케이션이 실제 부담하는 준비·복사 비용을 공짜로 처리하지 않는다.
- 실패·제한 초과·중단한 시도와 원본 소스·설정·바이너리 hash를 보존한다. 보조 시험의 결과로 주 시험을 통과 처리하지 않는다.
