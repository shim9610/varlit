# Cross-format benchmark at 10 GB, 2026-11-17

Varlit, SQLite, HDF5 and Parquet on the seven scenarios of
[`tools/format-bench`](README.md), each scaled to
10 GB of logical data. Library and harness at `6d8ca6d` (branch
`fix/mmap-integrity-matrix-traversal-c0yapu`), one repeat per engine and
scenario (`python3 run.py --data-gb 10`), tables from `report.py`.

These numbers come from a different machine than the result tables in the
harness README (24 cores, NVMe), so the two must not be compared row by row.
Ratios and order can change on other hardware, a physical disk in particular.

## Hardware and software

| | |
| --- | --- |
| Host | Cloud session container, Firecracker microVM on KVM |
| CPU | Intel Xeon Processor @ 2.10 GHz, 4 vCPUs, 1 thread per core, L3 260 MiB |
| Memory | 15 GiB, no swap |
| Disk | virtio block device `/dev/vda`, ext4 (`rw,relatime,discard`), mq-deadline scheduler; about 22 GB writable for the session |
| Disk, idle | 4 KiB `pwrite` + `fdatasync`, 3000 times: median 0.16 ms, p90 0.21, p99 0.36, p99.9 1.21, max 1.58 ms; 2 GiB sequential write with `fdatasync`: 493 MB/s |
| Disk, under load | while the bench writes at full rate the same probe showed p99.9 about 25 ms and a maximum about 96 ms (measured during the mixed-live analysis on this host) |
| OS | Ubuntu 24.04.5 LTS, kernel 6.18.44 |
| Toolchain | rustc 1.100.0, release builds |
| Engines | SQLite 3.54.1 bundled (rusqlite 0.41.1); HDF5 1.14.6 serial (hdf5-metno 0.15.1); Parquet via arrow-rs 60.1.0; zstd 0.14.3 |

The grid scenario runs under a 4 GiB memory cap (cgroup v1), so the data does
not fit in memory. The other scenarios run without a cap.

## Results

One table per scenario, with the parameters that decide it. Times are wall
clock; MB is the file size on disk at the end.

### grid: 6-D f32 array, growing time axis, 4 GiB memory cap (favors HDF5)

| engine | all reads s | time series ms | 16 sub-cubes ms | ensemble means ms | write s | MB |
|---|---|---|---|---|---|---|
| varlit | 1.69 | 58 | 900 | 59 | 29.4 | 9988 |
| hdf5 | 1.22 | 52 | 637 | 50 | 22.0 | 9935 |
| sqlite | 1.54 | 63 | 774 | 42 | 39.4 | 11352 |
| parquet | 2.49 | 80 | 1269 | 81 | 50.7 | 9996 |

HDF5 is fastest on reads and writes. Varlit is second on time series, third
on all reads and sub-cubes.

### oltp: accounts with dense ids, durable transfers (favors SQLite)

| engine | 1000 txn s | txn p99 ms | 20k cold points s | 20k warm points s | 200 branch sums s | load s | MB |
|---|---|---|---|---|---|---|---|
| varlit | 0.64 | 0.88 | 1.90 | 0.275 | 0.197 | 53.7 | 10865 |
| sqlite | 1.35 | 23.33 | 1.15 | 0.140 | 0.083 | 247.9 | 11685 |
| hdf5 | 2.20 | 3.24 | 7.78 | 3.002 | 0.350 | 41.4 | 10017 |
| parquet | 6.19 | 10.19 | 158.61 | 143.109 | 1.600 | 56.1 | 11628 |

Varlit (matrix, one account per cell) commits transactions 2.1x faster than
SQLite with a 26x lower p99. SQLite is faster on point reads (1.6x cold, 2x
warm) and on branch sums (2.4x).

### oltp-sparse: the same accounts with sparse 64-bit keys

| engine | 1000 txn s | txn p99 ms | 20k cold points s | 20k warm points s | 200 branch sums s | load s | MB |
|---|---|---|---|---|---|---|---|
| varlit | 1.53 | 9.82 | 2.09 | 0.191 | 0.186 | 208.7 | 13635 |
| sqlite | 1.54 | 20.87 | 1.28 | 0.134 | 0.080 | 278.7 | 13758 |
| hdf5 | 9.86 | 15.12 | 23.29 | 10.250 | 0.210 | 46.4 | 11556 |

Varlit (keyed storage) matches SQLite on transactions with half its p99.
SQLite is faster on point reads (1.6x cold, 1.4x warm) and branch sums
(2.3x). Varlit's load is 4.5x HDF5's, which writes a sorted array.

### analytics: append-only 12-column table, cold queries (favors Parquet)

| engine | Q1 group-by s | Q2 20 ranges s | write s | MB |
|---|---|---|---|---|
| varlit | 4.944 | 0.093 | 41.2 | 6140 |
| parquet | 5.363 | 0.087 | 46.6 | 6108 |
| sqlite | 106.656 | 0.139 | 147.0 | 11427 |
| hdf5 | 6.192 | 0.104 | 30.9 | 6218 |

Varlit is fastest on Q1; Parquet is 7 % faster on Q2. HDF5 writes fastest.

### mixed: three typed streams flat out, four live followers (favors Varlit)

| engine | x real time | publish p99 ms | inconsistent views | late reader catch-up s | write s | MB |
|---|---|---|---|---|---|---|
| varlit | 3.10 | 32.17 | 0 | 22.67 | 31.0 | 9972 |
| sqlite | 1.39 | 161.55 | 0 | 21.94 | 69.1 | 9988 |
| hdf5 | 2.55 | 81.30 | 64 | 35.54 | 37.8 | 9992 |
| parquet | 0.88 | 339.44 | 0 | 62.84 | 109.8 | 20083 |

Varlit has the highest throughput and the lowest publish p99. HDF5 followers
saw 64 inconsistent views (one stream ahead of another within a window).

### mixed-live: the same in real time, 10 ms freshness, every window durable

| engine | late windows % | B-only follower late % | seen before durable % | inconsistent views | publish p99 ms | MB |
|---|---|---|---|---|---|---|
| varlit | 1.93 | 1.75 | 94.32 | 0 | 4.06 | 9972 |
| sqlite | 40.84 | 35.27 | 24.95 | 0 | 42.98 | 9988 |
| hdf5 | 2.74 | 2.23 | 85.06 | 208 | 10.03 | 9992 |
| parquet | 100.00 | 100.00 | 11.70 | 0 | 325.08 | 20083 |

The writer groups up to 16 windows into one commit when it falls behind.
"Seen before durable" is the share of windows a follower saw before the
writer's commit for that window returned.

- Varlit misses the 10 ms bound in 1.9 % of windows. The late windows follow
  the fsync tail of this disk under load (see Hardware); they are not a
  regression (an A/B run of the earlier harness on this host showed 10.5 %).
- Varlit's commit uses a single barrier: the publication becomes visible to
  followers before the fsync that makes it durable has returned. 94 % of
  windows were seen in that gap. A crash in the gap can lose a window a
  follower has already seen. HDF5 shows the same (85 %); SQLite in WAL mode
  much less (25 %). Under the strict definition (nothing visible before it is
  durable) no engine meets the 0-loss bound here.

### cells: fixed 1 KiB cells updated in place, 64 per atomic update, four followers

| engine | updates/s | follower lag p99 ms | torn + corrupt reads | growth MB | initial load s | MB |
|---|---|---|---|---|---|---|
| varlit | 280 | 4.76 | 0 | 0 | 57.5 | 10092 |
| sqlite | 454 | 2.05 | 0 | -1 | 59.5 | 13369 |
| hdf5 | 151 | 4.77 | 3739 | 0 | 87.8 | 10077 |

SQLite is fastest: 454 updates/s against Varlit's 280, with a lower lag p99,
and no torn reads for either. HDF5 followers read 3739 torn or corrupt cells.

The SQLite row comes from a rerun of this scenario alone. In the full run it
failed with `SQLITE_FULL`: the harness loaded all cells in one transaction
with WAL autocheckpoint off, so the WAL held the whole 10 GB before the final
checkpoint copied it into the database, and the session's disk could not hold
both (a 2 GB run peaked at a 2.6 GB WAL). The load now commits and
checkpoints every 256 MiB (WAL peak 360 MB); this was a harness bug, not a
SQLite limit.

## Summary

| scenario | best | Varlit |
|---|---|---|
| grid | HDF5 | second on time series, third on full reads |
| oltp, dense | Varlit for transactions; SQLite for reads and aggregates | 2.1x SQLite on transactions; 1.6-2.4x slower on reads and sums |
| oltp, sparse | Varlit and SQLite level on transactions; SQLite for reads and aggregates | lower p99; slow load |
| analytics | Varlit on Q1, Parquet on Q2 | Q2 within 7 % |
| mixed | Varlit | highest throughput, no inconsistent views |
| mixed-live | Varlit on lateness | 1.9 % late; visible before durable in 94 % of windows |
| cells | SQLite | 0.6x SQLite's update rate, no torn reads |

## Reproducing

```
cd tools/format-bench
python3 run.py --data-gb 10 --out RUN_DIR
python3 report.py RUN_DIR
```

HDF5 1.14 must be on `LD_LIBRARY_PATH`. The run needs about 22 GB of free
disk; files are removed after each engine.
