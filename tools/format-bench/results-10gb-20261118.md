# Cross-format benchmark at 10 GB, 2026-11-18

Varlit, SQLite, HDF5 and Parquet on the seven scenarios of
[`tools/format-bench`](README.md), each scaled to 10 GB of logical data.
Library and harness at `ccf93a2` (branch
`fix/mmap-integrity-matrix-traversal-c0yapu`), one run per engine and
scenario (`python3 run.py --data-gb 10`), tables from `report.py`. No run
failed.

These numbers come from a different machine than the result tables in the
harness README (24 cores, NVMe), so the two must not be compared row by row.
Even on this cloud machine, the host changes between sessions: the previous
10 GB pass (kernel build `fc-v553`) was slower for most engines across the
board. Compare engines within this pass only. Ratios and order can change on
other hardware, a physical disk in particular.

## Hardware and software

| | |
| --- | --- |
| Host | Cloud session container, Firecracker microVM on KVM |
| CPU | Intel Xeon Processor @ 2.10 GHz, 4 vCPUs, 1 thread per core, L3 260 MiB |
| Memory | 15.7 GiB, no swap |
| Disk | virtio block device `/dev/vda`, ext4 (`rw,relatime,discard`), mq-deadline scheduler; about 22 GB writable for the session |
| Disk, idle | 4 KiB `pwrite` + `fdatasync`, 3000 times: median 0.26 ms, p90 0.51, p99 1.15, p99.9 2.45, max 3.07 ms; 2 GiB sequential write with `fdatasync`: 795 MB/s |
| OS | Ubuntu 24.04.5 LTS, kernel 6.18.44 (`fc-v595`) |
| Toolchain | rustc 1.100.0, release builds |
| Engines | SQLite 3.54.1 bundled (rusqlite 0.41.1, libsqlite3-sys 0.39.1); HDF5 1.14.6 serial (hdf5-metno 0.15.1); Parquet via arrow-rs 60.1.0; zstd 0.14.3 |

The disk probe was taken idle, after the pass. Under the bench's write load
the fsync tail is much longer (a previous session on this kind of host saw
p99.9 about 25 ms and a maximum about 96 ms).

The grid scenario runs under a 4 GiB memory cap (cgroup v1), so the data does
not fit in memory. The other scenarios run without a cap.

## Results

One table per scenario, with the parameters that decide it. Times are wall
clock; MB is the file size on disk at the end.

### grid: 6-D f32 array, growing time axis, 4 GiB memory cap (favors HDF5)

| engine | all reads s | time series ms | 16 sub-cubes ms | ensemble means ms | write s | MB |
|---|---|---|---|---|---|---|
| varlit | 1.60 | 58 | 880 | 43 | 23.0 | 9988 |
| hdf5 | 1.05 | 39 | 514 | 41 | 19.6 | 9935 |
| sqlite | 1.43 | 68 | 733 | 39 | 36.4 | 11352 |
| parquet | 1.91 | 189 | 903 | 71 | 37.8 | 9996 |

HDF5 is fastest on reads and writes. Varlit is third on all reads and
sub-cubes, second on time series.

### oltp: accounts with dense ids, durable transfers (favors SQLite)

| engine | 1000 txn s | txn p99 ms | 20k cold points s | 20k warm points s | 200 branch sums s | load s | MB |
|---|---|---|---|---|---|---|---|
| varlit | 0.57 | 1.05 | 1.82 | 0.113 | 0.110 | 40.5 | 10865 |
| sqlite | 0.96 | 20.09 | 1.39 | 0.104 | 0.082 | 218.5 | 11685 |
| hdf5 | 2.24 | 3.74 | 7.05 | 1.949 | 0.214 | 29.8 | 10017 |
| parquet | 5.97 | 8.84 | 150.10 | 130.456 | 1.342 | 42.8 | 11628 |

Varlit (matrix, one account per cell) commits transactions 1.7x faster than
SQLite with a 19x lower p99, and loads 5.4x faster. SQLite is faster on cold
point reads (1.3x) and branch sums (1.3x); warm point reads are level.

### oltp-sparse: the same accounts with sparse 64-bit keys

| engine | 1000 txn s | txn p99 ms | 20k cold points s | 20k warm points s | 200 branch sums s | load s | MB |
|---|---|---|---|---|---|---|---|
| varlit | 1.29 | 8.12 | 1.66 | 0.130 | 0.118 | 173.7 | 13635 |
| sqlite | 1.31 | 19.00 | 1.27 | 0.103 | 0.066 | 238.6 | 13758 |
| hdf5 | 8.80 | 13.03 | 17.93 | 9.019 | 0.224 | 34.1 | 11556 |

Varlit (keyed storage) matches SQLite on transactions with less than half its
p99. SQLite is faster on point reads (1.3x) and branch sums (1.8x). HDF5,
which writes a sorted array, loads 5x faster than Varlit.

### analytics: append-only 12-column table, cold queries (favors Parquet)

| engine | Q1 group-by s | Q2 20 ranges s | write s | MB |
|---|---|---|---|---|
| varlit | 5.012 | 0.096 | 37.7 | 6140 |
| parquet | 4.831 | 0.072 | 42.6 | 6108 |
| sqlite | 79.947 | 0.118 | 118.3 | 11427 |
| hdf5 | 6.170 | 0.100 | 25.8 | 6218 |

Parquet is fastest on both queries (Q1 by 4 %, Q2 by 25 %). HDF5 writes
fastest.

### mixed: three typed streams flat out, four live followers (favors Varlit)

| engine | x real time | publish p99 ms | inconsistent views | late reader catch-up s | write s | MB |
|---|---|---|---|---|---|---|
| varlit | 4.67 | 122.30 | 0 | 13.93 | 20.6 | 9972 |
| sqlite | 1.76 | 152.89 | 0 | 14.40 | 54.7 | 9988 |
| hdf5 | 4.20 | 85.64 | 74 | 13.78 | 22.9 | 9992 |
| parquet | 1.11 | 245.10 | 0 | 41.74 | 86.6 | 20083 |

Varlit has the highest throughput. HDF5 has the lowest publish p99, but its
followers saw 74 inconsistent views (one stream ahead of another within a
window). Varlit's publish p99 (122 ms) is well above the previous pass
(32 ms); the cause has not been examined.

### mixed-live: the same in real time, 10 ms freshness, every window durable

| engine | late windows % | B-only follower late % | seen before durable % | inconsistent views | publish p99 ms | MB |
|---|---|---|---|---|---|---|
| varlit | 2.27 | 2.09 | 95.64 | 0 | 4.36 | 9972 |
| sqlite | 25.11 | 21.00 | 23.64 | 0 | 25.67 | 9988 |
| hdf5 | 1.82 | 1.57 | 89.68 | 146 | 6.77 | 9992 |
| parquet | 99.98 | 97.70 | 17.88 | 0 | 138.54 | 20137 |

The writer groups up to 16 windows into one commit when it falls behind.
"Seen before durable" is the share of windows a follower saw before the
writer's commit for that window returned.

- Varlit misses the 10 ms bound in 2.3 % of windows, HDF5 in 1.8 % (with 146
  inconsistent views); SQLite in 25 %. The late windows follow the fsync tail
  of this disk under load.
- Varlit's commit uses a single barrier: the publication becomes visible to
  followers before the fsync that makes it durable has returned. 96 % of
  windows were seen in that gap. A crash in the gap can lose a window a
  follower has already seen. HDF5 shows the same (90 %); SQLite in WAL mode
  much less (24 %). Under the strict definition (nothing visible before it is
  durable) no engine meets the 0-loss bound here.

### cells: fixed 1 KiB cells updated in place, 64 per atomic update, four followers

| engine | updates/s | follower lag p99 ms | torn + corrupt reads | growth MB | initial load s | MB |
|---|---|---|---|---|---|---|
| varlit | 288 | 11.37 | 0 | 0 | 16.7 | 10092 |
| sqlite | 390 | 2.71 | 0 | -1 | 80.3 | 13369 |
| hdf5 | 175 | 5.34 | 2459 | 0 | 61.9 | 10077 |

SQLite updates fastest with the lowest follower lag; Varlit reaches 0.74x its
rate and loads 4.8x faster. Neither shows torn reads; HDF5 followers read
2459 torn or corrupt cells.

This scenario varies widely between runs (Varlit 270 to 495 updates/s,
SQLite 380 to 470 in repeated runs of the previous session). Timing the
stages showed why: without followers, about 2.5 s of a 4.5 s update phase is
the first fsync of about 16 checkpoints (about 150 ms each). A checkpoint
copies the ring's oldest generations into the tiles in place when the ring
is full, so the random cells are written back to scattered pages; an
ordinary publish fsync takes 0.3 ms (p50). Without followers Varlit does 440
to 540 updates/s against SQLite's 370.

## Summary

| scenario | best | Varlit |
|---|---|---|
| grid | HDF5 | second on time series, third on full reads |
| oltp, dense | Varlit for transactions and load; SQLite for cold reads and sums | 1.7x SQLite on transactions, p99 1 ms vs 20 ms |
| oltp, sparse | Varlit and SQLite level on transactions; SQLite for reads and sums | lower p99; slow load |
| analytics | Parquet | Q1 within 4 %, Q2 33 % slower |
| mixed | Varlit | highest throughput, no inconsistent views; p99 tail |
| mixed-live | HDF5 and Varlit on lateness; only Varlit without inconsistent views | 2.3 % late; visible before durable in 96 % of windows |
| cells | SQLite | 0.74x SQLite's update rate, no torn reads, 4.8x faster load |

## Harness corrections made before this pass

- The SQLite `cells` adapter loaded every cell in one transaction with WAL
  autocheckpoint off, so the WAL held the whole 10 GB beside the database
  and the run failed with `SQLITE_FULL` on this disk. It now commits and
  checkpoints every 256 MiB.
- The Varlit `cells` adapter wrote each cell with `write_matrix_cell_payload`
  and then `commit_matrix_cell` (the bitmap staged twice and the slot read
  back, about eight system calls per cell). It now writes and commits each
  cell, and loads runs of 4096 cells, with `write_matrix_run_bytes`.
- The `cells` metrics now include staging time (`stage_p50_ms`,
  `stage_p99_ms`, `stage_total_s`) beside publish time.

## Reproducing

```
cd tools/format-bench
python3 run.py --data-gb 10 --out RUN_DIR
python3 report.py RUN_DIR
```

HDF5 1.14 must be on `LD_LIBRARY_PATH`. The run needs about 22 GB of free
disk (the Parquet `mixed` file alone is 20 GB); files are removed after each
engine.
