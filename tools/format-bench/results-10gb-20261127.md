# Cross-format benchmark at 10 GB, 2026-11-27

Varlit, SQLite, HDF5 and Parquet on the seven scenarios of
[`tools/format-bench`](README.md), each scaled to 10 GB of logical data.
Library and harness at `f290766` (the head of PR #47, merged as `eca5e9a`:
sidecar-free streams, the cross-platform harness and `DeviceFlush`), one run
per engine and scenario (`python3 run.py --data-gb 10 --repeats 1`), tables
from `report.py`. All 26 runs passed the oracle.

The previous 10 GB pass on this kind of host,
[results-10gb-20261118.md](results-10gb-20261118.md), ran at `ccf93a2`,
before the sidecar removal. The host changes between sessions (this pass ran
on kernel build `fc-v880`, the previous one on `fc-v595`), so a difference
between the two passes is a lead, not a measurement. Compare engines within
one pass, and revisions with `ab.py`.

## Hardware and software

| | |
| --- | --- |
| Host | Cloud session container, Firecracker microVM on KVM |
| CPU | Intel Xeon Processor @ 2.10 GHz, 4 vCPUs, 1 thread per core, L3 260 MiB |
| Memory | 15.7 GiB, no swap |
| Disk | virtio block device `/dev/vda`, ext4 (`rw,relatime,discard`), mq-deadline scheduler; about 22 GB writable for the session |
| Disk, idle | 4 KiB `pwrite` + `fdatasync`, 3000 times: median 0.11 ms, p90 0.17, p99 0.29, p99.9 1.07, max 2.18 ms |
| OS | Ubuntu 24.04.5 LTS, kernel 6.18.44 (`fc-v880`) |
| Toolchain | rustc 1.100.0, release builds |
| Engines | SQLite bundled (rusqlite 0.41.1, libsqlite3-sys 0.39.1); HDF5 serial (hdf5-metno 0.15.1); Parquet via arrow-rs 60.1.0; zstd 0.14.3 |
| Durability | `device_flush: full`; on Linux this is the plain `fsync`/`fdatasync` for every engine (`DeviceFlush` differs only on macOS) |
| Cold reads | page cache evicted with `posix_fadvise(DONTNEED)`; `evict-check` went from 100 % to 0 % resident |

The disk probe was taken idle, after the pass. The run was not gated
(`--gate` off), as in the previous pass. The grid scenario runs under a
4 GiB memory cap, so the data does not fit in memory; the other scenarios run
without a cap.

## Results

Times are wall clock; MB is the file size on disk at the end. The figure in
brackets is the previous pass (2026-11-18) for the same engine.

### grid: 6-D f32 array, growing time axis, 4 GiB memory cap (favors HDF5)

| engine | all reads s | time series ms | 16 sub-cubes ms | ensemble means ms | write s | MB |
|---|---|---|---|---|---|---|
| varlit | 1.57 [1.60] | 66 | 793 | 43 | 23.1 | 9988 |
| hdf5 | 1.20 [1.05] | 42 | 670 | 39 | 19.9 | 9935 |
| sqlite | 1.58 | 53 | 802 | 41 | 39.0 | 11352 |
| parquet | 1.81 | 85 | 827 | 65 | 36.8 | 9996 |

HDF5 measured the lowest time on every read and the write. Varlit took
1.57 s for all reads (HDF5 1.20 s, SQLite 1.58 s) and 23.1 s to write (HDF5
19.9 s).

### oltp: accounts with dense ids, durable transfers (favors SQLite)

| engine | 1000 txn s | txn p99 ms | 20k cold points s | 20k warm points s | 200 branch sums s | load s | MB |
|---|---|---|---|---|---|---|---|
| varlit | 0.46 [0.57] | 1.09 [1.05] | 2.30 [1.82] | 0.105 | 0.093 | 39.9 | 10865 |
| sqlite | 1.25 [0.96] | 21.78 [20.09] | 1.93 [1.39] | 0.101 | 0.084 | 180.4 | 11685 |
| hdf5 | 2.31 | 8.46 | 6.52 | 1.663 | 0.245 | 28.8 | 10017 |
| parquet | 5.60 | 8.95 | 128.03 | 110.523 | 1.104 | 40.1 | 11628 |

Varlit took 0.46 s for the transfers (SQLite 1.25 s) with a p99 of 1.09 ms
(SQLite 21.78 ms), and 39.9 s to load (SQLite 180.4 s). SQLite took less time
on cold point reads (1.93 s against 2.30 s) and branch sums (0.084 s against
0.093 s).

### oltp-sparse: the same accounts with sparse 64-bit keys

| engine | 1000 txn s | txn p99 ms | 20k cold points s | 20k warm points s | 200 branch sums s | load s | MB |
|---|---|---|---|---|---|---|---|
| varlit | 1.91 [1.29] | 13.26 [8.12] | 1.88 [1.66] | 0.121 | 0.129 | 158.9 [173.7] | 13635 |
| sqlite | 1.80 [1.31] | 23.57 [19.00] | 1.21 [1.27] | 0.136 | 0.079 | 196.5 | 13758 |
| hdf5 | 7.85 [8.80] | 15.47 | 16.70 | 7.798 | 0.269 | 30.0 | 11556 |

Varlit took 1.91 s for the transfers (SQLite 1.80 s) with a p99 of
13.26 ms (SQLite 23.57 ms).
Both took about 40 % longer for the transfers than in the previous pass
(Varlit +48 %, SQLite +37 %), while HDF5 was faster. One run per pass cannot
separate the host from the revision here, and the macOS A/B
([results-mac/20261127.md](results-mac/20261127.md)) did not cover this
scenario, so whether Varlit regressed on sparse transfers is open.

### analytics: append-only 12-column table, cold queries (favors Parquet)

| engine | Q1 group-by s | Q2 20 ranges s | write s | MB |
|---|---|---|---|---|
| varlit | 3.859 [5.012] | 0.089 [0.096] | 32.3 | 6140 |
| parquet | 4.138 [4.831] | 0.067 [0.072] | 33.3 | 6108 |
| sqlite | 79.731 | 0.097 | 94.3 | 11427 |
| hdf5 | 4.997 | 0.077 | 23.4 | 6218 |

Varlit took 3.859 s for the group-by (Parquet 4.138 s) and 0.089 s for the
range queries (Parquet 0.067 s).

### mixed: three typed streams flat out, four live followers (favors Varlit)

| engine | x real time | publish p99 ms | inconsistent views | late reader catch-up s | write s | MB |
|---|---|---|---|---|---|---|
| varlit | 4.58 [4.67] | 78.60 [122.30] | 0 | 12.96 | 21.0 | 9972 |
| sqlite | 1.86 | 165.02 | 0 | 13.99 | 51.8 | 9988 |
| hdf5 | 4.12 | 88.36 | 58 | 15.18 | 23.4 | 9992 |
| parquet | 1.08 | 258.54 | 0 | 40.34 | 88.8 | 20083 |

Varlit wrote at 4.58 times real time with a publish p99 of 78.60 ms and no
inconsistent views. HDF5 wrote at 4.12 times real time and its followers saw
58 inconsistent views.

### mixed-live: the same in real time, 10 ms freshness, every window durable

| engine | late windows % | B-only follower late % | seen before durable % | inconsistent views | publish p99 ms | MB |
|---|---|---|---|---|---|---|
| varlit | 5.37 [2.27] | 5.31 | 0.00 [95.64] | 0 | 8.61 [4.36] | 9972 |
| sqlite | 24.72 | 20.99 | 23.33 | 0 | 29.04 | 9988 |
| hdf5 | 1.98 | 1.81 | 90.92 | 140 | 8.53 | 9992 |
| parquet | 99.11 | 92.93 | 23.18 | 0 | 98.96 | 20157 |

Varlit showed followers 0.00 % of windows before they were durable and no
inconsistent views. In the previous pass 95.64 % of its
windows were visible before they were durable; the change that publishes
stream data only once it is durable landed between the two passes (the
macOS A/B shows 0 % on both sides of the sidecar removal, so the sidecar
removal is not the cause). Waiting for durability costs lateness: 5.4 % of
windows were late against 2.3 % before, and the publish p99 doubled to
8.6 ms. HDF5 is less late but exposed 91 % of windows before they were
durable and showed 140 inconsistent views.

### cells: fixed 1 KiB cells updated in place, 64 per atomic update, four followers

| engine | updates/s | follower lag p99 ms | torn + corrupt reads | growth MB | initial load s | MB |
|---|---|---|---|---|---|---|
| varlit | 269 [288] | 7.45 [11.37] | 0 | -0 | 17.1 | 10092 |
| sqlite | 373 [390] | 3.11 [2.71] | 0 | -1 | 78.5 | 13369 |
| hdf5 | 170 | 4.58 | 3333 | 0 | 50.4 | 10077 |

SQLite made 373 updates per second with a follower lag p99 of 3.11 ms;
Varlit made 269 with 7.45 ms (11.37 ms in the previous pass) and took 17.1 s
for the initial load (SQLite 78.5 s). Neither showed torn reads; HDF5
followers read 3333 torn or corrupt cells.

## Summary

The per-metric values of this pass and the macOS run, and every metric where

## Reproducing

```
cargo build --release --locked --manifest-path tools/format-bench/Cargo.toml
tools/format-bench/target/release/varlit-format-bench evict-check RUN_DIR
cd tools/format-bench
python3 run.py --data-gb 10 --repeats 1 --out RUN_DIR
python3 report.py RUN_DIR
```

The run needs about 22 GB of free disk (the Parquet `mixed` file alone is
20 GB); files are removed after each engine. The raw `results.jsonl` of this
pass was kept in the session only.
